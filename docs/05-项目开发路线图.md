# 校园活动中心：个人开发路线图

> 用途：这是项目的长期执行清单。后续开发时，先更新本文件中的“当前进度”，再按对应阶段推进；每完成一个小目标，提交一次 Git。

## 1. 项目定位与成功标准

**一句话定位**：为校园学生提供集中浏览、搜索和报名活动的移动端平台，并帮助社团组织者发布和管理活动。

**目标用户**：学生、社团/活动组织者，以及项目管理员（第一阶段由开发者本人承担）。

**第一阶段不做的内容**：商铺、支付、私信聊天、推荐算法、推送通知、地图导航、正式现场扫码签到。这些需求放到 MVP 验证成功之后。

**MVP 成功标准**：

- 学生可以在手机浏览器中查看、搜索并报名活动。
- 组织者可以发布活动，并查看报名名单。
- 管理员可以审核活动。
- 找到至少 5 名同学试用，收集实际反馈。

## 2. 产品范围

### 2.1 学生端

1. 注册、登录和退出登录。
2. 查看活动列表、活动详情。
3. 按分类、关键词和时间搜索活动。
4. 报名、取消报名。
5. 查看“我的报名”。
6. 查看活动详情二维码（用于分享活动页面）。

### 2.2 组织者端

1. 申请或由管理员授予组织者身份。
2. 创建、编辑、取消活动。
3. 查看自己发布的活动。
4. 查看活动报名名单。

### 2.3 管理端

1. 审核待发布活动。
2. 管理活动分类。
3. 必要时下架活动或限制账号。

### 2.4 第二阶段：商铺模块

只有在活动模块有真实试用者之后再开始。包含店铺资料、菜单、优惠、位置和搜索；它应作为独立模块接入，不能阻塞活动 MVP。

## 3. 角色与权限

| 角色 | 主要权限 |
| --- | --- |
| 学生 | 浏览、搜索、报名、取消报名、查看个人报名记录 |
| 组织者 | 具备学生权限；可发布和管理自己创建的活动、查看报名名单 |
| 管理员 | 审核活动、管理分类、处理违规内容和账号 |

## 4. MVP 业务规则

1. 新活动默认状态为“待审核”，审核通过后才对学生公开。
2. 已报名用户不能重复报名同一活动。
3. 报名人数达到上限后，不能继续报名。
4. 活动开始前允许学生取消报名；开始后暂不允许取消。
5. 组织者只能编辑自己创建且尚未开始的活动。
6. 第一版的二维码仅用于打开活动详情页或活动报名页；动态签到二维码后续再实现。

## 5. 技术方案

| 层级 | 选型 | 负责内容 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite | 响应式手机网页、页面和接口调用 |
| 后端 | Java 21 + Spring Boot | REST API、业务规则、权限控制 |
| 身份验证 | Spring Security + JWT | 登录状态和角色权限 |
| 数据库 | MySQL | 用户、活动、报名等数据 |
| 接口测试 | Apifox 或 Postman | 调试和保存接口测试用例 |
| 版本管理 | Git + GitHub | 提交记录、文档和代码托管 |

本地开发先完成前后端联调；部署阶段再引入 Docker、Nginx、Redis 和云服务器，不提前增加复杂度。

## 6. 数据模型（第一版）

| 表/实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `users` | id、username、password_hash、role、status | 学生、组织者、管理员账号 |
| `organizations` | id、name、description、owner_id | 社团或主办组织 |
| `categories` | id、name、sort_order | 讲座、比赛、志愿、文体等 |
| `events` | id、title、content、category_id、organization_id、start_time、location、capacity、status | 活动主体 |
| `registrations` | id、event_id、user_id、status、registered_at | 学生报名记录 |
| `event_images` | id、event_id、url、sort_order | 活动海报或详情图片 |

关系：一个组织可发布多个活动；一个分类可包含多个活动；学生和活动通过 `registrations` 形成多对多关系。

## 7. 页面清单

### 第一版必须完成

1. 首页：近期活动、分类入口、搜索入口。
2. 活动列表页：关键词、分类、时间筛选。
3. 活动详情页：海报、时间、地点、主办方、名额、报名按钮。
4. 登录/注册页。
5. 我的报名页。
6. 发布活动页（组织者）。
7. 我发布的活动页和报名名单页（组织者）。
8. 活动审核页（管理员，初期可做得简单）。

### 后续页面

- 现场扫码签到页。
- 商铺列表、店铺详情、菜单和优惠页。
- 数据统计页。

## 9. Git 提交规范

每完成一个小目标就提交一次，提交信息使用英文前缀加简短中文/英文说明：

```text
docs: add development roadmap
feat: add event registration API
feat: build event detail page
fix: prevent duplicate registration
test: cover event capacity rule
```

提交前检查：代码能启动、不要提交密码/Token/数据库密码、不要把 `node_modules` 或构建产物提交到仓库。
