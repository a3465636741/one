# 校园活动中心：个人开发路线图

> 用途：这是项目的长期执行清单。后续开发时，先更新本文件中的“当前进度”，再按对应阶段推进；每完成一个小目标，提交一次 Git。

## 1. 项目定位

**一句话定位**：一个面向校园学生的活动信息导航平台，集中收集活动、提供分类搜索，并把学生引导至主办方的官方报名入口。

平台是信息“搬运和导航者”，不是活动的报名、签到或支付系统。活动详情页展示主办方提供的链接或二维码；学生点击链接或扫码后，进入主办方原有的问卷、公众号、小程序或其他报名页面。

**交付目标**：完成一个可演示、可部署、可由其他人运营的系统。开发者不承诺长期收集和维护某所学校的活动信息；交付后由客户或合作方负责内容录入、审核和日常运营。

### 为什么采用这个方向

- 对学生：不必在多个群聊、朋友圈和论坛中反复寻找活动。
- 对主办方：多一个展示入口，不必迁移原来的报名/签到流程。
- 对个人开发：避免账号体系、名额并发、签到防作弊、隐私数据和支付等高复杂度问题。

## 2. MVP 成功标准与边界

### 第一版必须达到

- 学生能在手机浏览器浏览活动、按关键词/分类/时间筛选。
- 学生能看到活动海报、时间、地点、主办方和活动说明。
- 学生能通过链接跳转或二维码扫码，进入主办方的官方入口。
- 管理员能录入、编辑、审核和下架活动。
- 至少邀请 5 名学生试用，验证他们能否更快找到感兴趣的活动。

### 第一版明确不做

- 站内注册、登录、报名、取消报名和报名名单。
- 站内签到、动态签到二维码和活动提醒。
- 支付、聊天、推荐算法、积分商城、微服务、多校区运营。
- 商铺模块（活动模块验证有效后再做）。

## 3. 信息来源与使用规则

活动信息可以来自公开的社团推文、论坛帖子、官方群公告，或由社团主动提交。每条活动至少记录来源链接或来源说明。

外部入口遵循以下规则：

1. 手机端优先显示“前往官方报名/活动页面”按钮，直接打开外部链接。
2. 同时可显示原始二维码图片，方便用户在电脑端浏览时用手机扫码。
3. 二维码/链接只由活动主办方或公开活动页面提供；不要伪造、修改或替换。
4. 对失效、取消或过期活动及时标记或下架。

## 4. 角色与功能

| 角色 | 主要权限 |
| --- | --- |
| 访客/学生 | 浏览、搜索、筛选、查看活动详情、跳转官方入口 |
| 主办方（后续） | 提交活动信息，等待管理员审核 |
| 管理员（开发者本人） | 录入、编辑、审核、置顶、下架活动，维护分类和来源 |

初版可只做“公开学生端 + 管理员端”，不做学生账号系统。主办方提交活动可先通过表单或私信收集，后续再开发提交入口。

## 5. 核心数据模型

| 表/实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `organizers` | id、name、description、contact | 社团、学院或活动主办方 |
| `categories` | id、name、sort_order | 讲座、比赛、志愿、文体等活动分类 |
| `events` | id、title、summary、content、category_id、organizer_id、start_time、end_time、location、cover_url、status、source_url | 活动主体和来源 |
| `event_entries` | id、event_id、type、url、qr_image_url、label | 官方报名/活动入口；`type` 可为 link 或 qrcode |
| `event_images` | id、event_id、url、sort_order | 海报或详情图片 |

关系：一个主办方可有多个活动；一个分类可包含多个活动；一个活动可配置一个或多个官方入口。

## 6. 页面清单

### 第一版必须完成

1. 首页：近期活动、热门分类、搜索入口。
2. 活动列表页：关键词、分类、日期筛选和活动卡片。
3. 活动详情页：海报、主办方、时间、地点、说明、来源、官方入口按钮和二维码。
4. 管理端活动列表：查看待审核、已发布和已下架活动。
5. 管理端活动编辑页：录入活动资料、来源、外部链接/二维码。
6. 管理端分类管理页。

### 后续页面

- 主办方提交活动页面。
- 收藏活动、订阅分类。
- 商铺列表、店铺详情、菜单和优惠页。

## 7. 技术方案

| 层级 | 选型 | 负责内容 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite | 响应式手机网页、搜索和详情展示 |
| 后端 | Java 21 + Spring Boot | 活动管理、审核、公开 REST API |
| 数据库 | MySQL | 活动、主办方、分类和外部入口 |
| 图片 | 初期使用公开图片 URL；后期接入对象存储 | 活动海报和二维码图片 |
| 接口测试 | Apifox 或 Postman | 验证管理和公开查询接口 |
| 版本管理 | Git + GitHub | 代码、文档和项目展示 |

第一版开发初期可暂不接入登录鉴权，先把公开浏览体验做出来；在演示和交付前，必须补上管理员登录和权限保护，避免任何人修改活动内容。

## 8. 六周执行计划

### 第 1 周：验证信息来源与页面原型

- [ ] 访谈 5～10 名学生：他们从哪里找活动、最想用什么条件搜索。
- [ ] 找 2～3 个社团负责人确认：是否愿意提供海报、链接/二维码和活动信息。
- [ ] 收集至少 10 条公开活动，确认字段是否足够。
- [ ] 画首页、列表、详情和管理端录入页的低保真原型。
- [ ] 更新 `docs/01-问题与目标.md`、`docs/02-用户与需求.md`。

**完成标志**：明确至少一种稳定的信息来源，并能写出一条活动的完整资料。

### 第 2 周：工程初始化与数据库

- [ ] 创建 Spring Boot 后端工程。
- [ ] 创建 Vue 3 + TypeScript 前端工程。
- [ ] 安装 MySQL，创建本地开发数据库。
- [ ] 建立 `organizers`、`categories`、`events`、`event_entries` 表。
- [ ] 准备 10 条真实或模拟活动数据。

**完成标志**：前后端都能启动，后端能从数据库读出活动数据。

### 第 3 周：后端公开接口和管理接口

- [ ] 实现活动列表、活动详情、分类查询接口。
- [ ] 实现关键词、分类、日期筛选。
- [ ] 实现管理员的活动新增、编辑、审核、下架接口。
- [ ] 实现外部链接/二维码入口的保存和读取。
- [ ] 用 Apifox/Postman 测试并保存接口集合。

**完成标志**：通过接口能录入活动，并让公开接口正确返回筛选结果和官方入口。

### 第 4 周：前端学生端

- [ ] 完成首页、活动列表、搜索和分类筛选。
- [ ] 完成活动详情页。
- [ ] 实现“前往官方入口”外链按钮。
- [ ] 实现二维码展示与加载失败提示。
- [ ] 在手机尺寸下检查页面布局。

**完成标志**：学生可完成“搜索活动 → 查看详情 → 打开官方报名入口”的流程。

### 第 5 周：管理端与内容质量

- [ ] 完成活动录入、编辑、审核、下架页面。
- [ ] 完成分类管理。
- [ ] 为活动添加来源字段，检查链接和二维码是否可用。
- [ ] 为过期活动添加过期状态或自动隐藏规则。
- [ ] 完善空状态、错误提示和活动缺图处理。

**完成标志**：你可以不改数据库，直接通过管理页面维护活动内容。

### 第 6 周：部署、试用与迭代

- [ ] 部署前端、后端和数据库，生成访问链接。
- [ ] 邀请同学试用，观察他们能否顺利找到外部入口。
- [ ] 修复最重要的 3～5 个问题。
- [ ] 更新 README：截图、技术栈、启动方式、在线演示链接。

**完成标志**：可向同学或面试官演示从发现活动到跳转官方入口的完整流程。

## 9. 交付与商业化准备

本项目的第一目标是提升技术并形成完整作品；“卖出”是可尝试的下一步，而不是必须兑现的结果。更现实的形式是软件定制或非独占授权交付，而不是你自己成为校园活动平台运营方。

### 潜在交付对象（由容易到困难）

1. 有运营能力的学生创业团队、校园媒体或社团联合会。
2. 学院/书院的学生组织、团委相关团队。
3. 需要校园信息展示能力的本地创业团队或技术服务团队。
4. 学校官方单位：通常涉及采购、合同、发票、数据安全与长期维护，不能作为第一个客户的唯一目标。

### 交付包必须包含

- 可运行的前端、后端和数据库脚本。
- 管理员账号初始化方法与管理端使用手册。
- `README`：本地启动、部署步骤、环境变量说明。
- 10～20 条演示活动数据及替换方式。
- 产品演示视频、页面截图和功能说明。
- 明确的内容责任说明：活动信息、二维码和外部链接由运营方确认和维护。

### 交付方式

- **作品演示**：用于简历、比赛、社团展示；不承诺商业使用。
- **定制部署**：为一个具体客户配置名称、主题、分类和初始数据，收取一次性交付费用。
- **非独占授权**：保留通用代码的所有权，可向不同客户部署；客户获得使用权。
- **独占买断**：只有在合同明确价格、范围、源码权属、后续维护责任时才考虑，不能随口把全部代码和权利交出去。

### 必须避免的风险

- 不抓取或公开非公开群聊、个人信息和报名名单。
- 展示海报、二维码和链接时保留来源；发现失效或被撤回时及时下架。
- 未获得学校官方授权前，不使用“山西大学官方平台”等表述或校徽。
- 客户的服务器、域名、内容审核和日常维护责任要在交付时写清楚。

## 10. Git 提交规范

每完成一个小目标就提交一次，示例：

```text
docs: refocus MVP as event discovery hub
feat: add public event list API
feat: build event search page
feat: add official event entry links
fix: hide expired events
```

提交前检查：代码能启动；不提交密码、Token、数据库密码；不提交 `node_modules` 或构建产物。
